# Open3D Print Code (Open3DPC) v2

## 1. Scope and core principle

Open3DPC v2 is a binary visual code intended for a two-colour physical object,
especially a 3D print. It stores only a deterministic data region and CRC in
logical matrix cells. Geometry communicates orientation, matrix dimensions,
capacity, and CRC algorithm; cells MUST NOT duplicate those properties.

The data region is self-delimiting: it is the payload, one terminator bit `1`,
and zero padding. A scanner therefore recovers not only the payload bits but
their exact count, and hands both to the application layer. The application
layer ([profiles.md](profiles.md)) selects a profile by that count.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. Terms are
defined in [README.md](README.md#terminology).

The only structural matrix position is `[0,0]`, reserved for the orientation
feature. It contains no payload, terminator, padding, or CRC bit.

An implementation MUST use the constants and algorithms in this document
exactly. No generator or scanner configuration may select another CRC
polynomial, bit reflection mode, orientation marker, terminator convention, or
dimension metadata for v2.

**v2 is the first published version.** An internal v1 without the terminator
existed in test prints only. A v2 implementation MUST NOT accept a v1 code and
MUST NOT offer a v1 mode.

## 2. Matrix and coordinate system

`H` is the number of matrix rows and `W` is the number of matrix columns.
Dimensions are always written `H × W` — for example, `4 × 7` means four rows
and seven columns. Portrait, landscape, and square matrices are all allowed.

Rows increase from top to bottom; columns increase from left to right. The
outer top-left corner is `(0,0)`. The physical width and height are:

```text
physicalWidth  = (W + 2) × M
physicalHeight = (H + 2) × M
```

`H` and `W` are positive unbounded integers at the physical-format level. The
standard compact UI may present a smaller candidate set, but it MUST NOT make a
positive geometry invalid for direct format use.

## 3. Physical geometry

Every ordinary binary matrix cell has size `M × M`. The normative default is:

```text
M = 1.6 mm
gap = M / 2 = 0.8 mm
frame thickness = M / 2 = 0.8 mm
```

If `M` is configurable, both gap and frame thickness MUST remain exactly
`M/2`; they are not independent parameters. A code consists of:

1. the logical binary matrix;
2. white gaps around the ordinary matrix cells;
3. a solid rectangular dark outer frame; and
4. one dark orientation feature attached to that frame.

The frame's outside contour MUST be a rectangle. The inner white opening starts
one frame thickness from each outside edge. Therefore every ordinary matrix
cell is an outside distance of exactly `M` from the frame's outside contour.

### 3.1 Orientation feature

After orientation normalization, the orientation feature denotes `[0,0]`. It
is a solid dark `M × M` square whose top-left corner is:

```text
(frame, frame) = (M/2, M/2)
```

It directly abuts the inner top and left faces of the outer frame. This is the
only dark physical connection from the frame into the matrix area.

The ordinary matrix-cell lattice DOES NOT move for this feature. Its right and
bottom edges are separated from cells `[0,1]` and `[1,0]` by white distances of
`M/2`. The feature overlaps only the top-left `M/2 × M/2` quarter of the
reserved logical position `[0,0]`; the rest of that reserved logical position
is white. No text or debug marker is placed inside the orientation feature.

### 3.2 Exact rendering coordinates

For an ordinary logical cell `[r,c]`, its physical rectangle begins at:

```text
x = (c + 1) × M
y = (r + 1) × M
```

The outer frame is dark in the rectangle from `(0,0)` to
`(physicalWidth, physicalHeight)`, with the internal rectangle from
`(M/2,M/2)` to `(physicalWidth-M/2, physicalHeight-M/2)` cut white before
drawing the orientation feature and dark bit-one cells. The above construction
MUST leave every non-orientation matrix cell isolated from the frame by white
space.

### 3.3 Outer quiet zone

A printed code MUST be surrounded on all four sides by a band of background at
least `M/2` wide, measured outward from the frame's outside contour. The band
MUST contrast with the frame and MUST contain no other mark, edge or frame.

The outside contour is the only complete rectangle a code has: the inner
opening is broken by the orientation feature. It is what a scanner looks for
first (§9, step 1), and without the band a frame can merge with the material
around it.

The quiet zone is a requirement on the object carrying the code. It is not part
of `physicalWidth × physicalHeight` (§2) or of the exported geometry (§8). A
scanner MAY use it as evidence and is not required to verify it.

*Informative.* `M/2` is the normative minimum. Whether it is enough on every
material, printer and camera has not been measured; a wider band is always
allowed.

## 4. Capacity and valid geometries

CRC width is derived only from `H`:

```text
C                = min(H, 10)
dataRegionLength = (H × W) − C − 1
payloadCapacity  = dataRegionLength − 1
```

The one cell subtracted from `dataRegionLength` is `[0,0]`. The one bit
subtracted from `payloadCapacity` is the terminator (§5.1): it is always
present, so it is never available to the payload. A geometry is valid if and
only if:

```text
H >= 1
W >= 1
payloadCapacity >= 2 × C
```

This minimum useful-capacity rule is normative. It prevents the CRC overhead
from exceeding half the payload. The maximum compact-v2 payload shown by the
standard UI is `10 × 10`: 88 payload bits plus terminator, CRC-10 and
orientation, but the format itself permits larger geometries. For `H >= 10`,
`C` stays 10.

At the default module size, selected physical dimensions MUST always be shown
prominently. Examples:

| Matrix | CRC | `dataRegionLength` | `payloadCapacity` | Physical size |
|---|---:|---:|---:|---|
| `1 × 5` | 1 | 3 | 2 | `11.2 × 4.8 mm` |
| `2 × 6` | 2 | 9 | 8 | `12.8 × 6.4 mm` |
| `2 × 7` | 2 | 11 | 10 | `14.4 × 6.4 mm` |
| `3 × 5` | 3 | 11 | 10 | `11.2 × 8.0 mm` |
| `4 × 4` | 4 | 11 | 10 | `9.6 × 9.6 mm` |
| `4 × 7` | 4 | 23 | 22 | `14.4 × 9.6 mm` |
| `10 × 10` | 10 | 89 | 88 | `19.2 × 19.2 mm` |

## 5. Canonical bit layout

### 5.1 Logical stream

Payload bits are first-bit-first. A generator MUST construct:

```text
DATA_REGION  = PAYLOAD || 1 || ZERO_PADDING
ENCODED_BITS = DATA_REGION || CRC
```

The single `1` after the payload is the **terminator**. It is mandatory: a
payload of `payloadCapacity` bits is followed by the terminator and no
padding; a payload longer than `payloadCapacity` cannot be encoded in that
geometry and the generator MUST reject it rather than omit the terminator or
truncate the payload. `ZERO_PADDING` is enough `0` bits to fill
`dataRegionLength`; it MAY be empty.

CRC is calculated over the complete data region — payload, terminator and
padding. Consequently, encoding the same payload in a different geometry
produces a different CRC; that is expected.

A payload MAY be empty (`length = 0`): the data region is then the terminator
followed by padding. Whether an empty payload means anything is the
application layer's business.

### 5.2 Physical data and CRC positions

CRC bits are logically the final `C` bits of `ENCODED_BITS`, but their physical
positions are fixed for visual clarity:

```text
CRC cell r = [r, W-1], for 0 <= r < C
CRC bit order = top to bottom
```

All other non-orientation, non-CRC cells receive `DATA_REGION` bits in
row-major order: row 0 left-to-right, then row 1, continuing top-to-bottom.
The traversal skips `[0,0]` and all CRC cells. Thus a scanner reconstructs the
logical stream by reading data-region cells in that traversal and appending the
right-column CRC bits in top-to-bottom order.

The terminator has no fixed cell: it is the data-region cell at traversal
offset `length(PAYLOAD)`. The first data-region cell is `[0,1]`.

For heights above 10, only the top ten cells in the rightmost column are CRC
cells. Lower cells of that column are ordinary data-region cells.

### 5.3 Recovering the payload

Given a validated data region, the payload is everything before the **last**
`1` bit, and its length is the number of those bits:

```text
t      = index of the last 1 in DATA_REGION        (reject if none)
PAYLOAD = DATA_REGION[0 .. t)
length  = t
```

A data region containing no `1` bit is not a code. It MUST be rejected as
`empty_data_region` even though its CRC (all zeroes, §6.1) matches. This is
what makes a blank matrix — frame and orientation feature with no other dark
cell — invalid.

## 6. CRC

### 6.1 Fixed convention

Open3DPC CRC is a canonical non-reflected bit-oriented division:

```text
init = 0
refin = false
refout = false
xorout = 0
input = DATA_REGION, first bit to last bit, MSB-first
output = zero-left-padded remainder, MSB-first
```

There is no byte order at the physical-code layer. Append `C` zero bits to the
data region, divide by the selected full polynomial using modulo-2 long
division, and emit the `C`-bit remainder.

Because `init = 0`, an all-zero data region has an all-zero CRC. Under v2 an
all-zero data region is structurally invalid (§5.3), so this identity never
admits a code; it remains in the vectors as a check on the arithmetic.

### 6.2 Full polynomial table

`FULL_POLYNOMIAL` includes both the leading `x^C` and constant `1` terms; no
leading or trailing term is implicit.

| Height | CRC width | FULL_POLYNOMIAL | Formula |
|---:|---:|---:|---|
| 1 | 1 | `0x3` | `x + 1` |
| 2 | 2 | `0x7` | `x² + x + 1` |
| 3 | 3 | `0xB` | `x³ + x + 1` |
| 4 | 4 | `0x13` | `x⁴ + x + 1` |
| 5 | 5 | `0x25` | `x⁵ + x² + 1` |
| 6 | 6 | `0x67` | `x⁶ + x⁵ + x² + x + 1` |
| 7 | 7 | `0xCB` | `x⁷ + x⁶ + x³ + x + 1` |
| 8 | 8 | `0x107` | `x⁸ + x² + x + 1` |
| 9 | 9 | `0x2FB` | `x⁹ + x⁷ + x⁶ + x⁵ + x⁴ + x³ + x + 1` |
| 10 and above | 10 | `0x48F` | `x¹⁰ + x⁷ + x³ + x² + x + 1` |

For `H >= 10`, the CRC width and full polynomial MUST remain CRC-10/`0x48F`.

## 7. Rendering and debug representation

Normal rendering MUST contain only the physical dark material and white
background: rectangular frame, orientation feature, and bit-one modules — the
terminator among them, indistinguishable from a payload `1`. Bit-zero
modules, padding, and ordinary gaps are white. The orientation square MUST
always be dark.

Debug rendering is diagnostic only and MUST NOT change normal/export geometry.
It MUST distinguish four cell kinds: payload bits, the terminator, padding
cells, and CRC bits; the structural orientation feature remains a solid black
square with no label. Padding cells MUST use a cross (`×`) label rather than a
binary-zero label. The terminator MUST use its own colour and a label that is
not `1`, so that the boundary between payload and padding is visible at a
glance. CRC zero and CRC one MUST use distinguishable shades. If labels are
shown, all cell labels use one fixed font size for a given preview.

## 8. Export

An implementation MUST support exact SVG and high-resolution PNG exports.
SVG dimensions MUST use the physical dimensions from Section 2. PNG raster
output MUST preserve the same geometry at sufficient resolution for scanner
testing.

Where STL is offered, it MUST preserve the exact frame, gap, module size, and
orientation connection. Material height is not part of the format. The reference
generator emits dark material as 4-connected watertight component shells with no
base plate, no overlapping volumes, and no internal vertical faces between
adjoining dark cells. Other generators MAY choose an equivalent watertight
representation.

## 9. Scanner contract

A compatible scanner MUST conceptually perform these steps:

1. Detect a rectangular outer dark frame.
2. Detect the unique `M × M` dark feature connected to its inner top/left
   faces; reject a missing, ambiguous, or partial feature/frame.
3. Rotate the observation in 90-degree increments until that feature is at
   normalized `[0,0]`.
4. Determine `M`, count `H` and `W` from physical geometry, and reject
   non-positive dimensions or a geometry failing Section 4.
5. Derive CRC width and full polynomial solely from normalized height.
6. Sample the logical cells, reject a missing/ambiguous sample, and skip the
   structural orientation position.
7. Read the data region row-major while skipping right-column CRC cells; read
   CRC cells top-to-bottom from the rightmost column.
8. Recalculate CRC over the complete sampled data region and reject on
   mismatch.
9. Locate the last `1` of the data region; reject `empty_data_region` if there
   is none. The bits before it are the payload; their count is its length.
10. Return the payload and its length — and nothing else — to the application
    layer ([profiles.md](profiles.md)).

The physical layer does not interpret those bits. A scanner MUST reject codes
with an incorrect CRC, any individual module inversion that causes CRC
failure, an empty data region, incomplete/partially visible frames, invalid
geometry, malformed orientation geometry, or a rotation that cannot be
normalized. **CRC never influences registration:** no cell is moved and no
lattice is preferred because doing so produced a passing checksum.

## 10. Conformance

Implementations MUST pass [vectors/v2.json](vectors/v2.json). The vectors
contain CRC and complete-matrix expectations for heights 1–10 and an above-10
saturated case, each with a full payload (empty padding) and a short payload,
zero/one/alternating edge cases, the recovered payload length, physical
dimensions at `M = 1.6 mm`, and the all-zero arithmetic cases. The negative
vector metadata defines required scanner rejection classes, including
`emptyDataRegion` and `payloadOverflow`.

Application profiles have additional semantic vectors; those checks occur
only after the physical conformance checks above succeed and the payload
length has selected the profile.
